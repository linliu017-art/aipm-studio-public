# 产品 PRD 编写与评审

将真实问题逐层转成可评审、可设计、可开发、可验收的产品需求。核心链路为：

**问题与证据 → 用户任务 → 分层目标 → 版本范围 → 流程与交互 → 系统能力 → 验收评测 → 上线反馈。**

## 范围与协作边界

- 负责产品需求定义及其变更。不要仅因写完 PRD 就进入技术计划、任务拆分或编码；若用户已明确要求后续开发，完成需求定义后再衔接对应工作流，不重复询问已获授权的事项。
- 工程规格和实现使用 `spec-driven-development`，引用已确认的 PRD，补充代码项目中的实现约束；不要在 PRD 中机械加入构建命令、源码目录或代码风格。
- 若已有立项报告，沿用其中有效的问题证据、目标与边界。若方向尚无依据，可先形成有假设标记的探索稿，并指出必须验证的事项；不要自动扩展为立项、市场研究等独立任务。
- 沿用用户已有模板、文档体系、术语和存储约定。已有原型、评测或规格时引用并核对，避免重复建立相互冲突的文档。
- 通用核心保持一致，详细程度随复杂度调整。简单功能可以是一页 PRD；适用的复杂模块再展开。不适用的栏目省略或简述原因，不制造占位章节。

## 按请求选择模式

- **新建或补全**：盘点材料，再按下方流程形成可评审草稿。
- **评审**：先读原文及用户指定材料，按核心链路检查；交付按影响排序的问题、原文位置或证据、影响及具体建议。区分发布阻断项与完善建议。用户只要求评审时不改正文。
- **更新**：定位变更及其依赖，修改受影响的范围、流程、规则、指标、权限、数据和验收，保留仍有效的内容，记录版本与变化。未决策的方案不得写成已确认要求。
- 用户限定只做某一阶段或模块时，遵守该范围，复用已有上下文，不强制重做整份文档。

## 信息与决策规则

1. 明确区分**事实、假设、建议、待决策项**。事实关联来源；没有证据的判断不得写成用户结论或业务数据。
2. 开始时用简短清单说明已有材料、关键缺口和影响方向的假设。优先阅读用户已给材料，无法读取时说明范围，不能声称读过未取得的内容。
3. 优先询问影响目标用户、核心任务、首版范围、关键风险或成功标准的问题。能从材料推断的常规选择先给建议并说明依据；不为每个栏目逐项盘问。
4. 缺少关键答案时仍完成不依赖答案的分析与草稿，清楚标注依赖。不得用默认值冒充批准，不得把高影响未决策事项藏在细节里。
5. 不预设每阶段结束都需要用户批准或结束当前轮次。先交付具体可评审结果；只有用户指定关口、必要决策或实际执行权限要求才暂停对应工作。
6. 不照搬参考项目中的阈值、工期、技术方案或承诺。每个数值注明材料依据、测算方式或“建议目标，待验证”。外部研究只在支撑当前需求确有必要或用户要求时进行，并引用来源。

## 编写流程

顺序用于检查依赖，可以迭代，不要求逐阶段停顿。一般分为方向、方案、交付三轮；已有结论直接复用。

### 第一轮：问题、任务与成功标准

**文档基础**

维护产品版本、文档版本、负责人、状态及变更记录；人员、日期、排期不明时标记待定。统一业务术语、指标和系统概念，关联原型、设计稿、数据与评测材料。

**问题与证据**

按“现状—痛点—影响—机会”分析相关业务、数据、质量、协作和知识沉淀问题。写清谁在什么场景完成什么任务、当前怎么做、哪里受阻、成本多大、为何现在解决。区分已观察的障碍和推测的原因。

**角色与任务旅程**

用户画像聚焦职责、专业能力、工作环境、核心任务、痛点、期望和权限，不填与设计无关的人口属性。还原现有旅程，再描述目标旅程；逐步记录输入资料、操作、判断、耗时或风险、期望结果及所需能力。明确哪些工作由系统辅助，哪些由用户确认。

**分层目标**

区分核心价值、商业、业务、技术与质量指标。选择能代表本产品价值的核心指标，不机械要求所有场景只有一个指标。每个关键指标说明定义、基线、目标、公式或评分方法、样本与分母、统计周期、数据来源及负责人。

对生成成功、使用、采纳和业务收益分别定义；明确去重、重复导出、修改幅度等影响口径的规则。整体质量指标与关键错误红线分别制定，不用整体平均值掩盖关键失败。检查跨章节目标是否矛盾。

### 第二轮：范围、流程与功能行为

**版本规划**

从目标旅程选出能完成核心任务的最小完整路径。功能表关联问题或任务，记录一级/二级功能、简明验收条件、优先级、依赖、里程碑、日期和负责人。未确认安排留待决策，不编造承诺。

优先级考虑任务必要性、结果可信度、问题频率与损失、替代方案及实现成本。明确本期不做及后续纳入条件。范围较大时建立稳定需求标识与能力分组，保留整体任务路径；工程模块拆分在后续工程规格中处理。

**三种流程视角**

- 业务流程：角色协作、业务状态、交付与流转。
- 用户操作流程：入口、输入、操作、判断、确认及结果。
- 系统处理流程：校验、数据、服务、处理依赖与返回结果。

复杂场景用三种视角交叉检查，简单场景可合并。图文应一致，正常、分支、人工确认和异常路径可走通；图片或原型不可访问时不得推断其细节。

**逐项需求契约**

采用“模块/功能—原型或界面依据—行为规则”的表达，每项重要功能覆盖：

- 对应问题与任务、角色、前提及入口。
- 输入字段、必填性、格式、默认值、校验及资料来源。
- 用户操作、业务判断、处理规则、输出与后续操作。
- 空白、等待、处理中、成功、失败等适用状态及反馈。
- 中断、取消、重试、恢复、重复提交等相关边界。
- 查看、创建、编辑、导出、删除等权限与数据范围；不能只写隐藏入口。
- 关键埋点与可验证的验收条件。

跨功能共用规则集中写并引用，不重复复制。让产品行为足够明确，同时保留工程实现空间。

**AI 专项（仅涉及 AI 时）**

读取 [references/ai-product.md](references/ai-product.md)，展开能力分工、工具、上下文、事实、提示词、人工确认和评测。普通产品不加载此附件。

### 第三轮：交付、验证与反馈

**非功能要求**

按实际需要覆盖性能、并发、可靠性、安全、易用性、可访问性、兼容性与可维护性。写清条件、衡量方法和目标依据。例如响应时延区分首反馈与全部完成；兼容性明确产品需要支持的环境；不把不相关标准一律设为强制要求。

**异常兜底**

每类重要异常写成“触发条件—系统动作—用户感知—恢复方式”。考虑输入或文件失败、资料不足、超时、网络中断等真实场景，说明重试/降级条件、工作保存、继续执行与人工介入。重试需要有终止条件，替代资料或输出要有可识别标记。

**验收与评测**

让业务专家或实际用户提供真实任务和判断依据，产品与技术将其转成可执行用例。覆盖功能、完整任务链路、关键红线、异常与恢复。验收条件说明前提、操作、可观察结果和通过标准。

根据任务规模与风险选择样本、重复运行和上线门槛，不固化原文的题数或参数。对关键输入、规则或能力的变更指定回归范围。标记尚未验证的可行性与结果，不把写入 PRD 的目标称为已实现。

**数据反馈**

按任务漏斗记录开始、成功、失败、放弃、修改、产出和反馈等有用事件。重要事件定义名称/标识、触发时机、关联任务标识、必要字段及指标用途。关注重复事件、漏报和口径；避免为无明确用途的数据埋点或采集多余敏感内容。

区分用户满意度、实际行为与成果质量，利用数据定位问题并安排迭代。

## 产物与完成检查

新建完整 PRD 或需要参考结构时，读取 [references/prd-template.md](references/prd-template.md)，按现有模板与范围裁剪；评审和局部更新无需强制重排原文。

按用户指定形式交付，未指定时给出可直接评审的文档。独立列出影响交付的缺口与待决策项，注明影响、建议及负责人（已知时）。不把探索草稿标为批准定稿。

交付前检查：

- 核心功能能否追溯到问题或任务，目标是否有数据口径。
- 版本范围、流程、交互、权限和输出是否一致。
- 正常与失败路径是否都能说明，用户工作如何保留。
- 验收条件能否观察，评测是否覆盖关键风险。
- 事实、假设、建议和待决策项是否清楚，引用是否真实可用。
- 变更是否同步到关联规则与验收，是否留下冲突版本。

简述交付内容及重要未决事项，不自动进入开发或外部发布。
