# 结构化长稿怎样交付

这份文件只用于用户明确规定文章结构、篇幅、图片、图表、文件格式，或者要求继续修改一份现有稿件的场景。普通创作不需要读取。

## 先把显式约束锁住

动笔前在内部记下用户已经决定的内容。

- 标题是否已经选定。
- 哪些标题、章节和顺序不能改变。
- 篇幅说的是正文、全文、汉字数还是可见字符。
- 图片需要占位、真实截图、原创示意图还是生成图片。
- 哪些关系确实需要表格或 Mermaid 图表。
- 来源放在正文附近、文末，还是另交事实表。
- 最终交付在聊天、写作块、Markdown 文件还是其他文档中。

用户说“禁止调整大纲结构”时，章节名、层级、数量和顺序全部锁定。只能在对应章节里补内容。不能合并、拆分、改名、另加前言、摘要和结语。发现原大纲有事实或逻辑问题，先指出具体位置，再等用户决定是否解锁。

显式约束互相冲突时，先保住事实边界和用户最新指令。无法同时满足的地方要在动笔前说明，不能悄悄选择一条。

## 当前稿件永远以用户最新版本为准

用户编辑过写作块、文档或草稿以后，这个版本覆盖模型早先输出和本地暂存稿。继续修改前先取得或重建最新全文，不从旧文件重新生成。

局部修改只碰用户点名的位置。没有得到许可，不顺手改标题、章节、语气、来源和其他段落。重新交付完整作品时，保留用户已经修改的文字、图片位置与结构。产品支持持续文档标识时，沿用同一个标识。

本地文件只是工作副本。它与用户可见稿件不一致时，用户可见稿件拥有优先权。需要把两者合并时，先列出差异，不能让旧副本覆盖用户编辑。

## 篇幅要用可复现的口径

用户说“正文约四千五百字”而没有另定口径时，默认统计正文段落里的汉字，排除标题、小标题、网址、Markdown 语法、图片路径、代码块、Mermaid 语法和文末参考资料。允许上下浮动约百分之十。

用户要求严格字符数时，先说明统计口径。严格目标不能靠重复结论、拉长过渡和增加无关背景完成。材料只能支撑较短篇幅时，回到主流程补材料或缩短。

长稿完成后可运行下面的检查。

```text
python3 scripts/check_delivery.py 稿件.md --target-han 4500
```

大纲另存为 Markdown 时，可以检查标题是否保持一致。

```text
python3 scripts/check_delivery.py 稿件.md --outline 大纲.md --target-han 4500
```

## 图片先分清身份

用户只要求图片占位时，按其指定格式原样保留，不擅自生成图片。

用户要求补图时，先判断图片属于哪一类。

- 真实产品界面、新闻现场和官方材料优先使用可核验的原图或截图，并保留来源。
- 原理解释、抽象流程和没有现成截图的内容可以制作原创示意图。
- 生成的界面图必须写明“示意图”，不能冒充真实产品截图。
- 装饰图只在它能帮助读者进入题目或控制版面节奏时使用。

替换图片占位时，直接在最新稿件的原位置替换。不要只把图片另交一份，也不要重新输出一个丢失用户编辑的旧版本。

项目内的 Markdown 交付物优先使用相对图片路径，保证整个目录移动后仍能打开。聊天中预览本地图片时使用应用要求的绝对路径。公众号后台通常需要重新上传图片，交付时把图片文件与文章放在同一输出目录。

## 图表只解决关系问题

Mermaid、表格和示意图用来解释文字难以迅速看清的关系。普通段落已经说清时，不重复画图。

- 有依赖、分支和返工路径时使用 `flowchart`。
- 有先后交互和确认往返时使用 `sequenceDiagram`。
- 有阶段日期时使用 `timeline` 或 `gantt`。
- 有层级、实体、类或状态关系时，分别选择能表达该关系的图。

图中的节点名称沿用正文用词。不要为了图表另造一套概念。图表出现以后，正文仍要交代读者应该看什么，不能让图替代关键判断。

交付前检查代码围栏是否闭合，Mermaid 类型是否正确，分支能否回到合理位置。用户随后要求把图转成图片时，保留可编辑的 Mermaid 源码，另交渲染结果。

## 交付前做一次约束核对

完成初稿和常规改稿以后，再核对下面几件事。

- 标题与章节层级是否和锁定大纲一致。
- 正文篇幅是否按约定口径落在范围内。
- 图片占位是否仍有遗漏，生成图是否明确标为示意图。
- Mermaid 围栏、类型和节点是否完整。
- 用户最新编辑是否全部保留。
- 交付文件里的图片链接能否在目标环境中打开。

这次核对只验证交付约束，不替代 `references/revision.md` 的文章审稿。
