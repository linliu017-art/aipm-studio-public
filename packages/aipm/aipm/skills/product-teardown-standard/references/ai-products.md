# AI 与 Agent 产品扩展框架

仅在产品核心价值依赖 AI、Agent、生成模型或自动化编排时使用。

## 1. 先验证结果，再拆 Agent

不要从“用了几个 Agent”开始。先验证：用户给出什么，最终得到什么，成品能否使用，失败时能否控制和恢复。Agent 数量、模型名称和动画式流程本身不构成价值。

AI 产品的体验可从四层评估：

1. 结果层：正确性、完整性、一致性、可消费或可交付程度。
2. 用户层：意图理解、澄清质量、控制权、反馈和修改成本。
3. 系统层：任务分解、协作、状态同步、错误隔离和断点恢复。
4. 模型与数据层：模型路由、知识使用、资产复用、评测和持续学习。

权重由任务风险决定。创作产品可重结果质量和控制感；高风险决策产品应提高正确性、可追溯与人工审批权重。

## 2. 判断产品形态

区分以下机制，允许混合：

- 单模型调用：一次输入得到一次输出。
- 工具增强单 Agent：一个决策主体循环调用工具。
- 固定工作流：步骤和分支主要由程序定义。
- Planner–Executor：规划与执行分离，适合长链路和审批。
- 多 Agent：多个角色有明确输入输出契约、状态边界与协作协议。
- 人机协作流程：关键节点由用户或专家批准、编辑或接管。

界面出现多个角色不等于后台存在多 Agent。寻找独立状态、差异化工具、输入输出契约、并行或串行依赖、失败隔离等证据。

先把产品放在“问答 → 固定工作流 → 单 Agent → 多 Agent”的自主程度光谱上，再判断具体实现。页面步骤固定不变更像工作流；任务变化时步骤随之重规划，更像 Agent；不同角色之间存在可观察的交接、独立状态或失败隔离，才更支持多 Agent 判断。拿不准时换一个结构不同的任务再次测试，不根据动画或营销名称下结论。

## 3. 角色逐个拆解

对每个 Agent 或自动化节点记录：

| 项目 | 要回答的问题 |
|---|---|
| 目标 | 它对最终结果负责什么 |
| 触发 | 谁在什么状态下调用它 |
| 输入契约 | 必需字段、可选字段、引用对象 |
| 输出契约 | 写入哪些字段，交给谁消费 |
| 工具 | 检索、数据库、生成、计算、外部 API、审批 |
| 状态权限 | 可读、可写、禁止触碰的字段 |
| 决策规则 | 澄清、路由、重试、回滚、升级人工 |
| 校验 | 格式、引用完整性、业务规则、质量评测 |
| 失败模式 | 幻觉、重复、卡死、脏状态、级联错误 |

若无法观察某项，标记未知并给验证办法。

## 4. 全局上下文与状态

把共享上下文视为项目的结构化“活 PRD”。检查是否存在：

- 项目元数据、版本、权限和任务状态。
- 用户目标、约束、偏好和审批记录。
- 上游产出与下游引用的稳定 ID。
- 资产 URI、来源、版本和复用关系。
- 依赖图、完成状态和错误状态。
- 修改后的影响范围、回滚点和审计记录。

重点验证四种操作：新增、读取、修改、删除/失效。检查修改上游对象后，下游引用是否同步，是否会出现孤儿资产、旧版本混用或跨 Agent 信息丢失。

## 5. 工作流与恢复

画出主流程，也要画出：信息不足、用户拒绝、单节点失败、工具超时、输出不合格、模型不可用、成本超限、连续重复输出等分支。

检查：

- 何时追问，何时自动补全。
- 何时需要显式审批。
- 修改是局部重跑还是全量重跑。
- 稳定节点如何定义，能否断点续传。
- 同一请求是否幂等，重复确认会不会触发重复执行。
- 连续失败后由谁介入，备用模型或人工路径是什么。

长链路、高耦合、需要审批的生产任务通常更依赖显式状态和 Planner–Executor；开放探索任务可以使用更灵活的 ReAct。根据任务特性判断，不把某一种架构视为通用答案。

把每个人工确认点标在流程中，并解释它为什么存在。常见理由只有三类：

- 成本高：错误可以重来，但重跑会消耗显著时间、算力、额度或金钱。
- 主观：结果好坏依赖人的审美、偏好或业务判断。
- 担责：操作会影响外部系统、真实用户、资金、权限或合规责任，错误难以撤回。

若一步操作成本低、可撤回且能局部修改，却频繁打断用户确认，应把它视为可能的交互负担；若高成本、主观或需担责的步骤没有确认与接管机制，应把它视为控制风险。确认点多少没有统一最优值，要回到目标用户的专业程度和产品承诺判断。

## 6. 模型、知识与工具路由

对每类任务建立“需求特征 → 候选能力 → 选择规则 → 回退方案 → 评测指标”的路由表。

检查路由是否考虑：质量、时延、成本、上下文长度、工具能力、风格或领域适配、隐私、地区可用性和稳定性。列出模型名称不等于解释路由。

若使用 RAG 或知识库，检查来源质量、切片与检索、时效、引用、权限、冲突处理和无答案策略。若使用风格库、模板库或技能库，检查新增能力后是否重新评测并更新适配关系。

## 7. 数据与壁垒

区分四类数据：输入数据、过程状态、用户反馈、结果与效果数据。判断它们是否形成闭环：

> 使用 → 结果 → 评价 → 标注/评测 → 路由或流程改进 → 更好结果。

通用模型 API 很少单独构成壁垒。更值得检验的是：领域工作流的结构化表达、专有评测集、可复用资产、反馈闭环、模型路由经验、深度集成、交付与服务体系。

## 8. AI 产品专项评分候选

按产品承诺选择维度并重新设定权重：

- 端到端任务完成与可交付性
- 事实正确性或生成质量
- 跨步骤、跨对象和跨轮次一致性
- 意图理解与主动澄清
- 用户控制、编辑、审批和回滚
- Agent 协作与状态同步
- 知识、工具与模型路由质量
- 资产复用与数据沉淀
- 稳定性、时延和单位任务成本
- 安全、隐私、权限与可追溯性

不要只测最佳样例。至少包含正常任务、信息缺失任务、修改任务和故障恢复任务。

## 9. 架构结论模板

用以下六层概括，而不是堆技术名词：

1. 交互层：用户如何表达、观察、编辑和批准。
2. 编排层：任务如何拆分、路由、并发和回滚。
3. 角色/技能层：每个节点的职责、契约和工具。
4. 状态与知识层：共享上下文、资产、RAG、版本和权限。
5. 模型与工具层：选择、调用、校验、回退和成本控制。
6. 基础设施层：队列、存储、监控、评测、安全和可观测性。

最后说明哪些结论是直接观察，哪些是反向推断，以及最小验证实验是什么。
