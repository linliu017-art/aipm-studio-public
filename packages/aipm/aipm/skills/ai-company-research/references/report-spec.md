# 公司调研报告规范

本 reference 只定义 `company` 模式读者可见的最终报告。`client` / `investor` 使用各自扩展中的通用 frontmatter，不继承这里的 company 专属必填字段和五模块结构。研究步骤、工具、Gate、子代理分工和内部证据标签不写入正文。

## 1. Frontmatter

新报告至少包含：

```yaml
---
title: 企业简称 · 公司调研
report_id: stable-slug-YYYYMMDD
subject: 工商或注册全称
mode: company
depth: quick
market_status: listed|private|subsidiary|institution|unknown
version: v1
as_of: YYYY-MM-DD
generated_at: YYYY-MM-DD
---
```

- `subject` 是本报告的事实主体；品牌或集团边界在正文说明。
- `market_status` 决定财务写法。无法确认时用 `unknown`，不得猜。
- 同一主体更新时保持 `report_id` 稳定并递增 `version`。

## 2. 深度与篇幅

### quick

用于第一次筛查。结论先行，每个核心维度只保留能改变判断的信息；所有章节仍存在，证据不足的章节写明缺口，不用背景常识填充。

### standard

用于合作评估或较完整了解。展开产品线、技术证据、财务趋势、商业质量、2–4 个可比对象和最近变化；关键结论尽量有原始来源与独立佐证。

### deep

用于重大决策。展开主体树、连续财期、分部与地区、管理层与治理、竞争分板块、冲突证据、敏感性和附录。深度来自证据与分析，不来自重复章节。

## 3. `company` 五模块结构

`company` 默认交付一份整合报告，只使用以下五个 H2。业务报告与技术报告各自可独立阅读，但共享主体、截止日、产品命名、来源 ID 和贯通矩阵，不拆成两个内容重复的文件。`quick` 可以缩短表格和段落，不能删除任一模块；不适用或公开未披露时，用一段自然语言说明边界。

```markdown
# {企业简称} · 公司调研

## 公司总览
## 业务报告
## 技术报告
## 财务、商业质量与风险
## 来源与信息缺口
```

每个模块内部使用 H3 / H4 组织，不能为了保留旧模板把原有章节继续平铺为 H2。

### 3.1 公司总览

让读者在 3 分钟内完成主体识别和第一轮判断。推荐内部顺序：

- **决策摘要**：公司到底做什么、靠什么赚钱，最有证据的经营与技术强项，财务可得性、最重要风险和当前结论。
- **主体与范围**：法人、品牌、集团、母子公司、股票代码、地域、报告截止日，以及哪些数据不属于目标主体。
- **关键变化与竞争位置**：最近一年对判断有影响的新增、收缩、转向，以及按业务线核实的主要竞对和替代方案。
- **综合判断与下一步**：只给公开证据可以支持的结论和动作。

复杂集团可用简表或一张必要关系图。避免“行业前景广阔、技术实力雄厚”之类无证据套话；不在总览提前堆完后文全部细节。

### 3.2 业务报告

业务报告单独拿出来也应让读者理解公司如何经营。推荐内部顺序：

- **本章结论与范围**：一句话判断核心业务、收入逻辑和当前证据强弱。
- **产品/服务组合**：区分核心在营、增长/新增、实验/愿景、历史/收缩与待核实。
- **经营链贯通矩阵**：以主要产品为行，连接客户/付费方、交付、技术、变现和来源。
- **客户、获客与交付**：使用者和付费方分开；说明直销、渠道、平台、招投标、自助购买等路径。
- **变现、竞争与近期变化**：按业务线说明收费方式、商业化证据、竞对/替代与最近变化。
- **业务质量判断**：给出规模化条件、反对证据和失效情形。

贯通矩阵使用以下列，不随意省略或改成彼此无法对照的多张表：

| 产品/服务 | 客户与付费方 | 交付方式 | 技术支撑 | 变现方式 | 来源 |
|---|---|---|---|---|---|

同一字段可写“公开未披露 / 无法确认”，不能拿行业惯例填空。产品组合和矩阵高度重叠时可以合成一张表，但六个贯通字段必须完整可辨。

### 3.3 技术报告

技术报告单独拿出来也应让读者理解产品承诺如何实现，以及公开证据能支持到哪一步。推荐内部顺序：

- **本章结论与证据边界**：先说明能确认什么、不能确认什么。
- **产品—技术映射**：沿用贯通矩阵中的产品命名，说明对应技术能力、原始证据、成熟度与自研边界。
- **研发资产与投入信号**：区分产品/API 文档、论文、专利、开源、标准、认证、招聘与公司宣传的证明力。
- **依赖与技术风险**：包括外部模型/平台/云服务、数据、供应链、安全、合规、可扩展性与关键人依赖中有证据的部分。
- **技术判断与待验证项**：说明哪些产品承诺已经得到技术证据支持，哪些仍只是公司自述或未知。

技术证据不足时必须降级：

- 只有可运行产品或产品文档：可以确认用户可见能力，不能推定底层全自研。
- 只有招聘、演讲摘要或营销材料：只写研发方向/公司自述，不写成生产技术栈或商用事实。
- 没有有效证据：保留“可见产品能力 + 公开未知 + 待验证问题”，不要生成猜测性架构图。
- 只有在原始材料明确披露组件、数据流、模型/供应商、部署边界及相互关系时，才描述或绘制技术架构。

专利、论文、开源、招聘与白皮书是不同强度的证据，不用数量代替质量。公司技术报告可引用少量专利作为证据；专利检索、IPC、专利族、权利要求、FTO 或组合评价仍属于专项任务；仅在可用时交给 `tech-mining`，缺少时说明能力边界。

### 3.4 财务、商业质量与风险

本模块把数字与商业解释放在一起，避免财务表与业务逻辑相互脱节。推荐内部顺序：

- **财务与资本**：按主体类型使用下列口径。
- **商业质量**：付费方、获客、定价、合同周期、续费/复购、客户集中、交付人力、平台/渠道依赖、护城河与切换成本。
- **风险与反对证据**：监管、诉讼、知识产权、财务、客户/渠道、技术、治理和执行风险中与本公司相关的部分；包含最可能推翻主结论的证据和失败模式。
- **决策含义**：哪些结论已足以行动，哪些需进一步验证。

- `listed`：写清报告期、币种、单位、合并口径；呈现收入、利润/亏损、经营现金流、研发和与商业模式相关的分部指标。
- `private` / `unknown`：若无公开财报，明确说明公开财务局限，再呈现融资和经营代理信号；不估造营收。
- `subsidiary`：把母公司集团数据与目标子公司数据分开。
- `institution`：按机构类型写基金规模、管理资产、出资与投资节奏，不套用企业利润表结构。

没有查到处罚不能写“无风险”。尽调、法律、审计或 FTO 专项未做时不得冒充完成。

### 3.5 来源与信息缺口

最后一个模块集中承载可追溯性，不在前四章重复粘贴来源清单。推荐内部顺序：

- **来源**：定义正文全部来源 ID。
- **信息缺口与待确认**：只列会改变业务、技术、财务、商业质量或风险判断的缺口，并说明建议向谁索取什么材料或做什么验证。

信息缺口不是内部审计日志。不要暴露搜索失败、抓取状态、子代理、工具名或 Gate；用面向读者的自然语言说明当前公开信息边界。

## 4. 来源格式

正文在相关主张后使用 `[S01]`、`[S02]`。公司总览、业务报告、技术报告和财务/商业质量/风险模块各有来源 ID，或在相应判断处明确写“公开未披露 / 本轮公开渠道未见 / 无法确认 / 不适用”。

最后一个 H2 模块内的来源小节使用：

```markdown
## 来源与信息缺口

### 来源

| ID | 来源 | 发布方/类型 | 发布日期 | 访问日期 | 支持内容 |
|---|---|---|---|---|---|
| [S01] | [标题](https://example.com) | 交易所公告 | YYYY-MM-DD | YYYY-MM-DD | 财务与分部 |

### 信息缺口与待确认

- 需要验证的关键问题，以及建议获取的材料或访谈对象。
```

要求：

- 正文引用的 ID 必须有定义；定义的来源应在正文被使用。
- 链接直接指向原文，不用搜索结果页代替。
- 来源发布日期未知时写“未标明”，不要编日期。
- 页面持续更新时仍记录本轮访问日期。
- 用户材料没有 URL 时，来源名应链接到可访问的绝对本地路径，并写日期和页码；公开来源仍优先给可点击网页链接。

## 5. 数字与表格

- 表头或每个数字同时说明币种、单位和期间，不能让读者猜。
- 同一表格使用可比口径；无法比较的数字分表或加明确注释。
- 百分比、同比和人均等派生指标保留计算分母；重要结果抽样复算。
- 精确数字来自审计、监管、合同或可验证原始数据时保留精确；第三方估计保留区间与估算口径。
- 表格只承载比较关系；单一事实用句子即可。
- 行内粗体标签后继续写正文时留一个空格，例如 `**结论：** 正文`；写成 `**结论：**正文` 在部分 CommonMark 渲染器中会裸露星号。

## 6. 确定性表达

正文自然区分：

- “监管披露/年报显示……”：已证实。
- “公司称/官网列示……”：公司自述。
- “第三方估算……”：保留来源与方法。
- “据此判断/更可能……”：分析判断，附条件与反证。
- “本轮公开渠道未见……”：检索范围内未知，不等于不存在。

不要把内部的 L0–L5、Gate、抓取状态、子代理或工具名当成面向读者的章节。

## 7. HTML 派生

定稿 MD 后使用 `scripts/build_report_html.py` 生成同 stem HTML，再运行严格审计。HTML 不维护第二套正文。生成、重写或验收 HTML 时完整读取 `company-html-layout.md`。

HTML 的信息层级借鉴飞书富文档：摘要、指标、表格、并列信息和风险块按内容需要组合，让重点先被看见；不追求组件数量或“每章一个卡片”。飞书 XML 标签、emoji、内部证据标签和排版过程不得进入 HTML 正文。

如果报告出现 Mermaid，只在关系复杂且图比文字明显更清楚时使用；图源码需可回退，失败不能吞掉正文。当前模板通过 CDN 加载渲染依赖；CDN 不可达时显示完整 Markdown 原文，图表库不可用或渲染失败时保留图源码。此降级不提供完整富排版，不是离线版；用户要求离线 HTML 时，必须先内联依赖或更换离线模板并重新做浏览器验收，不能把当前产物称为离线可用。

## 8. 禁止项

- 不编造客户、收入、利润、团队规模、路线图、技术栈、融资或市场份额。
- 不把注册资本、融资额、GMV、合同上限或用户数当作收入。
- 不把母公司财报直接归给子公司或品牌。
- 不把岗位、薪资、候选人、面试题、Offer 建议、IPC/FTO 清单混入 `company` 报告。
- 不默认拆出内容重复的业务报告、技术报告或“精简版”；五个模块保存在同一份内容真源。
- 不因技术章需要完整感而生成无来源的系统架构、模型清单、数据流、部署方式或自研结论。
- 不为凑结构增加 SWOT、PEST、AARRR、Mermaid 或长附录。
- 不在正文解释“本次优化、上一版、执行了哪些步骤”。
