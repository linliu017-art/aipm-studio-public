# Client / Investor 模式扩展

这两个模式建立在统一公司底图上，只增加本次会面所需内容。不要把岗位面试资产带入。

## 通用报告元信息与来源

两种模式均在 Markdown 开头提供以下 frontmatter，`mode` 按实际选择 `client` 或 `investor`。这些是生成器与严格审计的通用字段，不继承 company 的五模块章节结构或 `market_status` 必填要求；可选填写 `depth`，填写时须为 `quick` / `standard` / `deep`。

```yaml
---
title: 主体简称 · 拜访作战地图
report_id: stable-slug-YYYYMMDD
subject: 研究主体全称
mode: client
version: v1
as_of: YYYY-MM-DD
generated_at: YYYY-MM-DD
---
```

文件名以 `_vN.md` 结尾，`version` 与文件名一致；更新时保持 `report_id` 稳定并递增版本。正文以自然语言区分公司自述、已查证事实、分析判断与公开未知；使用 `[S01]` 等来源 ID，并在“来源”小节定义原文链接、发布方/类型、发布日期、访问日期及支持内容。用户材料可链接到可访问的绝对本地路径，不编造公开 URL。未标明发布日期时如实说明。

## Client

除公司底图外，重点确认：

- 本次机会的业务真相：现状、问题、预算、时限、验收和已承诺事项
- 采购信号、现有技术栈、现有供应商、替代方案与客户自建可能性
- 决策链：业务发起人、技术评估者、采购、财务、法务、最终拍板人
- 我方方案能解决什么、不能解决什么、最小验证怎样设计
- 商务与实施锚点：数据、集成、安全、资源、周期、验收与下一步

推荐附加章节：

1. 机会背景与真实需求
2. 决策链与关键人
3. 现状、替代方案和采购信号
4. 我方切入、边界与最小验证
5. 对方可能问的问题
6. 我方 discovery questions
7. 会议议程、风险与后续动作

会议纪要、RFP、邮件、合同等一手材料证明“本次机会中的陈述或约定”。与公网冲突时并列说明主体、时间和口径，不机械让任一方覆盖另一方。

问题清单生成前读取 `discovery-question-quality-standard.md`。问题质量高于数量；每题必须能改变需求、预算、决策、方案或下一步判断。

## Investor

对象是投资机构而非普通经营企业时，重点确认：

- 管理主体、基金名称、存续期、币种、规模与募集状态
- 投资阶段、票面区间、地域、行业主题和出手节奏
- 近期已投、退出、跟投和组合冲突
- 决策合伙人、项目来源与投决流程
- 我方项目与其投资逻辑的真实匹配、反对面与潜在条款

推荐附加章节：

1. 机构与基金主体
2. 当前投资主题与出手节奏
3. 近期案例与组合冲突
4. 决策人和投决流程
5. 我方叙事、匹配与差异化
6. 估值/条款锚点的适用边界
7. 双向问题、风险与下一步

基金“规模”必须区分目标规模、已募集、已缴与管理资产；单笔新闻不能代表稳定票面区间。

## 拜访后回流

收到会后纪要、录音或复盘时：

1. 把新材料登记为本次机会的一手证据。
2. 输出“原预判 vs 现场事实”差异，重点更新业务、痛点、预算、决策链和下一步。
3. 保留旧版本，生成新的同版本 MD+HTML 文件对。
4. 只把经多次验证、可跨对象复用的经验写回 Skill；写回前需用户明确同意。

现场原话与公开事实的证据角色不同。前者能更新机会判断，不能自动改写企业公开事实。
