# Agent 工坊方法与范围

本工作台适配 Hubo 的 MIT 项目 agent-workshop 中的需求维度、组件目录和选型规则。模型撰写、规则执行、检查结论和版本保存分别记录，不把一次模型回复当作全部流程完成。

## 需求问题

根据当前缺口询问，不要求每次完整盘问。

1. 要达成什么，怎样算做成？
2. 给谁用，在什么场景下使用？
3. 用户从输入到拿到结果，完整过程是什么？
4. 需要哪些外部动作、系统、API 或数据？
5. 领域规则和专业资料从哪里来？
6. 什么不能做，哪些数据或动作需要确认？
7. 工具失败、幻觉、超时或越权时怎么办？
8. 如何评估完成率、准确率、时延或成本？没有数字时记录待确认。

## 规则选型

`get` 返回完整十四项特征及其问题，不必记编号。yes → 必选，later → 二期，unknown → 待确认，no → 放弃。s01 Agent Loop 与 s02 工具系统是 Agent 产品的基础项。除基础项外，第一版必选组件达到三个时，s15 集成 Harness 为必选；包含二期的组件达到三个时，s15 为二期；否则放弃。这是设计规则，不是向运行中的工作台安装这些组件。

只有明确的否定或足以排除该能力的产品范围才能判 no；未提及不自动等于 no。选择依据是模型判断，规则只保证相同判断得到相同选型，不保证模型的判断一定正确。本适配器不运行上游的三次模型投票。

## 五要素和七层

五要素为工具、知识、观察、行动、权限。方案应解释需要什么动作、依靠什么资料、怎么观察结果以及谁可以批准动作。

工具 layer 使用字符串编号：1 交互层，2 产品层，3 Agent 编排层，4 模型层，5 能力集成层，6 数据层，7 基础设施层。方案中的层次图由程序生成，用于组织设计，不是根据运行轨迹发现的真实拓扑。

## 工作台集成范围

可用能力是同一模型会话内的需求整理、规则选型、结构与引用一致性检查、Markdown PRD／方案生成、项目内版本保存。用户事实仍需真实材料与确认支持。检查不能证明方案语义正确，版本快照也不等于用户已批准。

保存技术方案后，后台会使用当前模型发起独立审稿并保存建议报告；项目页也可重新触发。工作台的只读源码分析通过已选目录和文件行号证据提供反推 PRD 与差距报告，不执行代码验收。原项目的特征投票、模拟试玩、Python 启动器和代码骨架生成没有移入这个适配器。需要这些能力时另按明确任务处理，不能声称它们已经执行。当前授权不自动覆盖后续代码生成、部署或外部操作。
